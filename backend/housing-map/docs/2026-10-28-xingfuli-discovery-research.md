# 幸福里小区租房链接发现：只读实测

日期：2026-10-28，Asia/Shanghai。仅调研，不修改服务代码、不写生产关联、不启动生产采集任务。

## 结论

名称搜索已找到可用入口：`GET https://m.xflapp.com/f100/api/search`。此前失败记录中的 `/f100/api/search_api/rent` 是已验证的同小区列表分页入口，不能据此断言名称搜索不可用。本次成功来自当前网页公开脚本中的搜索调用和参数，不是猜测接口或处理验证码。

从搜索结果获取房源 ID 和真实 `neighborhood_id`，再核验房源详情、同小区列表及目录位置，能够找到可供现有采集器使用的入口。未实现自动发现，也未验证全部已收录小区的覆盖率。

## 当前收录范围

通过用户提供的 NAS SSH 地址，在现有 `housing-map-backend` 容器内读取运行中 API：

- `/api/directory/communities?admission_state=admitted&page_size=100&page=1`，以及第 2 页。

## 搜索入口证据及复现参数

从 `https://m.xflapp.com/zufang/hz` 实际引用的公开资源读取：

- [8018.a306b660.js](https://lf3-xfl.bytescm.com/obj/xfl-static/fproject/fe_mobile/static/js/async/8018.a306b660.js)：搜索函数合并 `city_id`、`offset`、`otherQuery`，按 `house_type=3` 选择租房搜索 channel，调用 `/f100/api/search`。
- [main.416c4d3e.js](https://lf3-xfl.bytescm.com/obj/xfl-static/fproject/fe_mobile/static/js/main.416c4d3e.js)：`hz=1853`，`F_SEARCH_RENT=94349530177`。
- [SearchMobx.853004cf.js](https://lf3-xfl.bytescm.com/obj/xfl-static/fproject/fe_mobile/static/js/async/SearchMobx.853004cf.js) 及 [7032.1eae1e31.js](https://lf3-xfl.bytescm.com/obj/xfl-static/fproject/fe_mobile/static/js/async/7032.1eae1e31.js)：查询字段合并、`rent_list` 页面口径及翻页传递 `search_id` 的方式。

成功请求参数：

```text
GET https://m.xflapp.com/f100/api/search
city_id=1853
house_type=3
channel_id=94349530177
full_text=璞悦湾
count=20
offset=0
page_type=rent_list
```

无需登录、Cookie 或签名生成代码。人工探测每批串行请求之间至少间隔 5 秒。接口为网页内部接口，不是承诺稳定的开放 API。脚本资源名、参数和响应都可能变化。

成功 JSON 为 `status=0,message=success,data.items[]`；条目含字符串 `id`、`neighborhood_id`、`title`、`display_subtitle_list`。不能将搜索 `total` 或条目数当合格整租样本数。

通过 NAS 的 housing-map 容器独立复验“璞悦湾”搜索和对应列表：两次均 HTTP 200，搜索 status=0，首屏各 20 条，真实小区 ID 均为 `6584028761644073220`。说明当前 NAS 出口可读，不只本机可读。

## 必须过滤的误命中

1. **不存在名称仍然成功并返回房源。** 搜索 `幸福里不存在小区验证20261028`，HTTP 200/status=0，首屏 20 条来自多个无关小区。`house_list_open_url` 仍回显查询词。因此 HTTP 成功、status=0、查询词回显、items 非空四者均不能单独证明真实命中。不能把它解释为目标小区，更不能据此自动绑定。
2. **完整名可能失败，别名成功。** “三盛大家·汝悦美境府”返回多个无关小区；“汝悦美境府”返回 15 条同小区 `7231807376527982652`。详情和同小区列表核验通过，列表 14 条并 has_more=false，位置在萧山。该样本当前未收录，只证明别名回退必要。搜索与列表条数差异也说明搜索数不能当统计数。
3. **主名称可能包含多个分区和不同平台身份。** 东方郡已有证据表明至少三个来源 ID 并存，尚未确认它们之间的完整覆盖关系，不应擅自合并或自动选区。
4. **浏览器 UI 仍然异常。** 本轮从真实页面搜索“璞悦湾”，导航至带 full_text 的页面后超过一分钟仍为“正在努力加载”。首页标题还显示北京，首屏条目却位于杭州。网页 UI 的失败不等于后台公开搜索接口不可用，标题也不能作为城市身份证据。

## 后续实现建议与未完成范围

建议的发现流程：当前 admitted 集合 → 复用已有有效关联 → 主名称/可信别名逐个有界搜索 → 从结果提取不同 neighborhood_id 的候选 → 详情核对完整小区名、行政区、坐标及分区 → 验证种子和同小区列表 → 唯一且证据充分才自动关联，歧义进审核 → 复用现有采集与统计。

必须保持 provider+真实小区 ID 隔离、种子 ID 独立保存、已有人工绑定/解除/拒绝决定保护；无关推荐应归为“未找到匹配候选”，不能变成候选、零房源或成功绑定。没有精确身份响应信号时，应依靠候选身份核验，不能只检查 keyword 回显。

本轮没有：扫描全部 155 个、确认东方郡三个 ID 的覆盖关系、证明长期稳定或种子下架恢复、写生产关联、变更用途/准入、部署、产出租金快照。原始网络响应保存在本机临时目录，仅将与小区身份相关的事实写入报告，不纳入经纪人个人资料。

已确定的事实：租房名称搜索为零、小区搜索找到分区身份、另一个不分区身份的详情/租房列表仍可读，三个来源 ID 并存。不能推断三个 ID 的创建时间先后、完整覆盖关系，或断言平台内部具体索引实现；索引遗漏/实体关联不一致仅为可能解释。此前“未找到入口”结论已被进一步验证更新。

这说明只按标准名/别名搜索租房接口不足以发现全部来源。后续发现设计应允许“小区搜索 + 已核验公开小区页实际租房链接”作为补充入口，再验证 seed 与 neighborhood_id；小区搜索本身也可能只返回分区身份，不能保证覆盖。来源身份和实际房源仍需逐一核对，未改动生产目录或绑定。
