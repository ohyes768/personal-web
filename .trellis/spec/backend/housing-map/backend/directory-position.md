# Known-community Amap position status

Explicit collection-pipeline-v2 activation extends positioning to candidate identities, accepts nonresidential building subjects and classifies from the selected POI. See [the v2 contract](./collection-pipeline.md); legacy instances retain the rules below.

## 1. Scope / Trigger
Applies to directory_position.py, directory_position_state.py, directory_workflow inventory/API, DirectoryFlowWorkspace and PositionPanel. Runs only after explicit directory-flow migration. Position evidence never creates sources/masters, establishes residential use, changes actual addresses, or reactivates ignored Amap discovery records.

## 2. Signatures
External prefix `/api/map/directory/workflow` (backend `/api/directory/workflow`):
- GET `/catalog?position=matched|pending|review|not_found|error|manual` filters before pagination, alongside existing district/market/type filters.
- GET `/catalog/{cid}/position` returns position plus `revision` (SHA256 of complete master, linked-source rows and admission payload).
- POST `/catalog/{cid}/position/query`, no body: explicit known-name retry; returns current position plus `errors:string[]` for durably saved query outcomes.
- POST `/catalog/{cid}/position/confirm` accepts `{revision,poi_id,coordinates_verified?:boolean}` for an existing server-side candidate, or `{revision,longitude,latitude,address}` for a verified manual GCJ02 point. `coordinates_verified` defaults to false and uses strict boolean validation.
- GET/POST/DELETE `/positions` retain the existing persistent/cancellable batch job.
- `position_view(target, records=())` is a pure projection; `position_one(...,client=None,cancelled=...,force=False)` performs bounded lookup then optimistic publication. `PositionOutcome(ValueError)` means an outcome was persisted; ordinary stale/eligibility ValueErrors remain conflicts.

## 3. Contracts
- Store additive `amap_position` in the master payload: identity fingerprint (id/name/aliases/district/actual address), state, checked_at, candidates, selected, error and optional confirmed_at. No schema migration or startup upstream calls. API position projection omits the internal identity token.
- matched requires genuine Amap POI identity evidence; historical_amap/TMSF IDs/coordinates alone remain pending. Existing source `coordinate_evidence.source=amap` with a real POI ID and valid GCJ02 position may supply legacy matching evidence; ignored/unlinked sources cannot.
- manual records include explicit chosen POIs and manually entered coordinates; absence of a POI ID must say so. Manual origin/evidence on the master or active source is protected, including later manual edits overriding a previous automatic result.
- Batch snapshots current admitted targets, processes pending/error only, skips matched/manual/review/not_found without constructing a client. Explicit single retry can re-query matched/review/not_found; manual results remain protected. Keep256-request budget,2s pauses, cancel/restart-interrupted/shutdown behavior. Queries use the existing server key configuration; no key-bearing URL enters reports.
- Batch reporting is by outcome, not failure: the job state tracks updated/review/not_found counts plus failed (genuine transport/config/stale conflicts) and a per-state `skipped_by_state` breakdown. Review/not_found outcomes are persisted as retryable entries tagged with their state, but they are expected results — `phase` stays `succeeded` unless `failed > 0`. The UI headline shows 补全/转待确认/高德无此地点/查询失败 and an 未参与本轮 breakdown by state instead of 补全/跳过.
- Lookup keeps exact full-name/alias, supported district, residential categories 120300-120304 plus mixed-use 商住两用楼宇 120203 (TMSF residential projects often sit in Amap mixed-use buildings; plain offices 120201 and the catch-all 120000 stay rejected; compound typecodes like `120302|120203` are accepted when any part is whitelisted), and boundary validation. Name comparison flattens both sides before equality/containment: parenthetical notes, middle dots (·・･) and generic estate suffixes (小区/花园/公寓/大厦/公馆/邸/苑/院/府) are dropped, so 中海·钱塘山水 matches 中海钱塘山水 and 积家 matches 积家小区; the shorter flattened side still needs length >= 3. Name filtering also accepts containment (loose) hits: a POI name and a community name/alias containing each other count as candidates when the shorter normalized side has length >= 3. An untruncated result (count <= 25) with exactly one name-matched candidate auto-matches regardless of loose (containment) naming or address differences; multiple candidates, or any candidate under truncation (count > 25), persist review candidates and never choose silently. In-district POIs that pass normalization but fail the name check stay visible as suspect candidates (`name_matched=False`), appended after name-matched ones and sorted by name_similarity in review; suspects never qualify for auto-binding (the single-candidate trust rule counts only name-matched candidates), and confirming a suspect uses the existing manual confirmation flow. A review with empty candidates now only means a truncated result with zero in-district POIs, which the UI answers with manual-positioning guidance. When the primary name yields no name-matched candidates and the result is untruncated (count <= 25), the lookup retries up to 3 normalized-deduplicated aliases in order and stops at the first candidate hit (loose hits count); alias retry requests are not added to the batch per-community `requests` count, so the budget still counts communities and upstream requests stay bounded at <= 4 per community. Empty reliable matches persist not_found; transport/config failure persists error. A failed/ambiguous explicit re-query retains the last valid match and error, without clearing coordinates.
- Preserve any existing valid master/source/historical-file map position during automatic POI completion; selected POI coordinates remain separately inspectable. Only explicit human confirmation replaces the map point. Geographic address remains separate from TMSF actual address. Changed identity invalidates old automatic POI state; retaining map coordinates never implies the new identity matched.
- Network work is outside writer transactions. Publication compares complete master/source/admission snapshot and re-evaluates current eligibility inside the writer; cancelled responses cannot write. Confirmation accepts only the saved candidates under current identity and supplied revision. Every selected candidate must retain its current district and valid in-district GCJ02 coordinates. A candidate missing map address requires explicit `coordinates_verified:true`, persisted with state=manual and confirmed_at; keep the original empty address and POI ID/type, never copy the source address into Amap evidence. Manual points without a POI still require a real address, finite GCJ02 values and the correct district boundary. Single writes and batch starts serialize through the existing job lock; running batch refuses single writes.
- UI keeps the POI status filter and a general detail entry. Position details follow basic community information; individual query/retry buttons, the standalone view-position action, and manual coordinate inputs are removed. Only review state exposes comparable candidate cards and explicit confirmation; other states show results only. Candidate links appear after selection, while IDs/coordinates/timestamps stay in collapsed details. Bulk completion remains in collection tasks (pending/error only; not_found is still skipped). Refresh the full detail after a successful operation to avoid stale geographic address display. Persisted query time and human confirmation time are distinct. Bulk does not follow the list's search/state filters; its card explicitly targets all admitted pending/error entries.

## Candidate presentation and layered catalog filters
- The position panel opens with one status line describing the current result: missing address, multiple subjects and name mismatch are cautions, query failure is an error, and the generic old error text is never re-read as "missing address". The repeated candidate-type list and the candidate dropdown are replaced by candidate cards: name, address (or "高德未提供地址") and the leaf type on separate lines, the full graded type in a collapsed detail. Reference candidates sit in a collapsed "相关地点，仅供参考（数量）" list and are never selectable.
- A single candidate with a POI id and valid coordinates becomes the current review target without submitting anything or pre-checking the map verification box; several candidates start unselected and use native radio inputs inside a fieldset/legend with label cards. The confirmation button follows the review content and always states the concrete reason it is disabled; busy blocks selecting, checking and submitting.
- Selection and the map-verification mark are bound to revision + POI id: changing candidate or revision drops the mark. A confirmed payload keeps revision/poi_id and adds `coordinates_verified:true` only for an addressless candidate that passed the map check; the empty Amap address stays empty and is never replaced by the source address.
- Catalog filters are layered per tab and share one definition across the request, the visible controls and the active-condition summary, so a hidden condition never influences the result. 已收录 keeps search/area/new-or-second-hand/position state visible and folds use-review, auction and rental; 待处理 keeps search/area/source use/position state and folds use-review; 不收录 keeps search/area/source use and folds use-review. 法拍待关联 keeps its own search, include-skipped and sync actions; 租金来源 keeps its own workspace.
- Every select has a visible label and an explicit "全部…" default. Folded filters show how many conditions are active. The summary lists only the conditions actually sent to the current tab, each removable on its own, and "清空筛选" empties q, district, position, market, property_type, use, auction and rental and returns to page 1. The default 滨江 area counts as an active condition. Switching tabs keeps search and area and clears the tab-specific filters, closes the detail and invalidates the old request; refreshing keeps all current conditions, and no URL or localStorage persistence is added.
- The 200ms throttle, AbortController, pagination fallback and stale-response protection stay in place. While loading the count reads "更新中…" instead of presenting the previous total as the result of the new conditions.

## 4. Validation & Error Matrix
- Inactive flow409; unknown/deleted/not-admitted/stale target or stale candidate409. DB/filesystem failures503.
- Invalid enum/revision/numeric bounds/non-finite input422. Missing/wrong-district manual point or forged/stale candidate409.
- Query review/not_found/upstream failure200 with saved state and explanatory errors. A stale result must never be downgraded to200 merely because an older checked_at exists.
- Active batch + single query/confirmation409. Empty/all-complete batches succeed without an upstream key.

## 5. Good / Base / Bad Cases
Good: history geocoder point → pending/has_coordinates → POI lookup adds evidence while retaining original map point → user explicitly confirms candidate if a location change is needed.
Base: two name-matching POIs, or a single candidate under truncation → review; user selects one with latest revision → manual, next batch skips it. Source edit during HTTP → conflict, no publication.
Bad: label every valid coordinate as matched, use the TMSF ID as a POI ID, clear an old point on lookup failure, or restore deleted discovery sources to show a badge.

## 7. Wrong vs Correct
Wrong: `if valid_position(c): skip_lookup()` or render `coordinate_evidence.source_id` unconditionally as POI.
Correct: `position_view(c, matched_sources)` requires Amap POI evidence, preserves historical coordinates separately, and defaults batch work to pending/error states.

## Catalog position presentation
- The catalog has a single 高德定位 column using the same labels as the filter: done=已定位 (matched/manual), review=待确认, todo=待处理 (pending/not_found/error). Compact badges retain the specific state in their title. Map visibility (map_status) is shown separately in the detail dialog as 地图显示状态, not as a second position column.

## Boundary with the use-category review
- The position lookup and the [Amap use-category review](./use-review.md) share the name matching rules in `poi_names.py` but run independent requests: position keeps the residential whitelist and stores a POI identity, the review drops the `types` filter entirely to see every category and stores a use verdict. Position evidence never establishes residential use and use-review evidence never establishes a map point.
- `amap_position` and `use_review` are separate additive payloads with separate identity fingerprints; neither invalidates the other and neither rewrites the other when it is refreshed.
