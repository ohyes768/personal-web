# Community directory contract

> 2026-11-03: Fang is retired. The directory keeps historical Fang source records readable, but they are never a current rental source, never contribute residential-use evidence and never get re-imported from the old mapping ledger. The only current rental source is Xingfuli; the generic directory write paths refuse new Fang associations while historical reads, unlink and ignore keep working.

> After explicit `tmsf-directory-v1` migration, [TMSF directory workflow](./directory-flow.md) supersedes multi-source admission/review and defines task eligibility. Stored history and pre-migration behavior remain readable.


Residential visibility now follows [Community admission](./community-admission.md). Source matched/pending/ignored still describes identity association; residential review/exclusion must never call whole-community deletion.

The UI and candidate operations now follow [Unified community review](./community-review.md). The raw source tab and separate auction binding panel are replaced by residential/review lists; legacy identity APIs cannot bypass human review locks.

## 1. Scope / Trigger
Applies to community_registry.py, community_directory.py, directory_collection.py, directory_routes.py, CommunityManagement.tsx and community identities consumed by map/price/rental/auction code. User requested one maintained directory in the existing deployment, without fresh-deployment seed or multi-version compatibility design.

## 2. Signatures
- `prepare_directory(DATA_DIR)` backs up current editable inputs to directory-backup once, imports existing IDs/decisions into community_registry.sqlite3, and stores meta.prepared. Restart does not reseed. The same SQLite directory is authoritative thereafter. Since the Fang retirement it no longer imports the old Fang mapping ledger or its candidates; an already prepared registry is left untouched.
- `CommunityRegistry`: communities(deleted=False), sources(), ingest(record), candidates(record), auto_associate(), associate(rid,cid), unlink(rid,cid=None), create_from_source(...), update(...), merge(cid,target), delete(cid,reason), restore(cid), ignore_source(rid), restore_source(rid), resolve(cid), is_ignored(source,kind,sid), events(cid).
- Tables: communities(id,payload,deleted,merged_to), sources(id,source,kind,sid,payload,cid,status,method,evidence,ignored_by), rejected(rid,cid), events(seq,cid,action,payload,created_at), meta(key,value). Source identity UNIQUE(source,kind,sid). Writes use transactions and foreign keys.
- DirectoryJob persists collection_job in meta; thread/event cancellation; restart marks unfinished run interrupted; shutdown joins the worker.

## 3. Contracts
- Existing IDs remain stable; new IDs use local- prefix. Names are not globally unique. Names/aliases are independent from source raw names; NFKC/whitespace normalization never drops phase/directional suffixes.
- New automatic associations require exact name/alias, unique full-name candidate, same district plus exact address or GCJ02 positions within 100m. Missing/ambiguous evidence remains pending; manual decisions and rejected pairs override auto. Geographic closeness alone never associates records.
- Delete means whole community + all currently associated identities, including multiple TMSF or auction sources. It disables subsequent independent detail fetches and business display. History remains. Restore explicitly reactivates records ignored by that community deletion; independent pending-source ignores remain unchanged. Unlink/reject is separate and does not delete the community.
- Source ID renames stay ignored; a new ID with a deleted name is pending and displays possible_deleted, not a global name blacklist. Laipai uses asset/auction identity, preserves observed auction_ids for skip checks across existing rounds.
- A community has at most one current rental source, and it is the Xingfuli one. Conflicting manual/auto rental associations return409. Historical Fang associations stay in the registry as read-only records; they are not a second active source and do not block the current merge or binding decisions. Multiple other source identities are allowed.
- Name collection uses the TMSF current list only; Amap regional discovery has been removed at user request; legacy Fang/Laipai records remain readable and rental/auction collection uses independent entry points. Unmapped records can become new communities manually, regardless of a TMSF ID. Collection is independent of rental mapping. The Fang name adapter is deleted with the Fang collector; directory discovery only accepts TMSF.
- Historical Fang samples stay with their source record and survive manual association, but they are read-only history: current rent queries never fall back to them, and no current snapshot is derived from them. Current rent data comes only from the published Xingfuli snapshot for the currently bound source.
- Existing price snapshot IDs are associated through current TMSF mappings; local-only entries are never requested as TMSF IDs. Deleted auction identities disappear even from unmatched auction lists; once registry exists, name fallback cannot override explicit unlink.
- Runtime DATA_DIR defaults to backend/housing-map/data; HOUSING_DATA_DIR can point to an isolated QA directory. Amap only supports geographic enrichment for already known communities; it does not discover community names. Key resolution: AMAP_WEB_SERVICE_KEY, GAODE_API_KEY, then scripts/_gaode_config.py; never put keys or request URLs into reports/logs. NAS compose forwards the server key separately from the frontend JS map key.
- The polygon scan, subdivision, regional pagination, AmapIncomplete and discovery adapter are deleted. Keep AmapClient.search_name/normalize_poi for bounded known-name position enrichment, API-key sanitization and shared geographic validation. Preserve legacy amap sources/associations/manual decisions and historical collection coverage/errors in SQLite; the management source filter offers only TMSF, Fang and Laipai; historical Amap evidence remains readable through source details and history APIs. New collection reports and controls do not present Amap coverage or a source selector. Since the Fang retirement the Fang entry is a read-only 房天下（历史） label: it can be viewed and explicitly unlinked/ignored, but never confirmed, enabled or collected.
- Name collection follows pagination to source exhaustion, detects repeated pages as incomplete, and uses two-second request delays, independent source failures, cancellation and report counters. Shared list pages may still contain ignored records; filter them before independent detail requests. No claim of complete regional coverage.
- TMSF directory collection publishes each name then fetches that community's property type/address with the shared `tmsf_property_type` service. Check the detail name against the list name/alias; challenge, wrong-target and missing-type pages are errors. Preserve raw mixed labels (no substring inference). CLI and directory share this parser and request validation.
- Source records store `property_type`, `property_type_url`, successful `property_type_captured_at`, latest `property_type_checked_at` and `property_type_error`. Reuse successful same-name facts for 30 days; retry missing/expired/failed facts. Failure preserves previous facts, records a per-source/property_type error and reports partial completion; failed attempts retain the last effective type; missing or conflicting use remains pending (see [enrichment](./community-enrichment.md)). Known ignored identities skip details, including after the delay; cancellation retains already published names.
- Management computes residential state from current effective associations, for both communities and pending sources; no stale residential_classification.json lookup. Legacy property_types.json is read by TMSF source ID until integrated effective facts supersede it; failed enrichment preserves the last valid standalone fact. Unlink/rebind/delete immediately changes classification. Explicit residential/nonresidential evidence is required; 公寓/其他/mixed/unknown labels and conflicting sources remain pending. Nonresidential records are retained, not deleted automatically.
- Residential classification: tmsf property types (住宅/别墅/排屋/写字楼/商贸/车位) produce a per-community state of residential / non_residential / pending / unknown. Since the Fang retirement no rental sample feeds the classification, so a community with only a historical Fang record stays 待核对 instead of becoming 住宅. tmsf `其他` and mixed signals stay pending until verified.
- Filter pipeline: scripts/filter_residential_communities.py consumes the classification report and writes binjiang_residential_communities.json / binjiang_pending_communities.json / binjiang_non_residential_communities.json. The import (prepare_directory) prefers the residential list and excludes the non_residential ids, while leaving sources for non_residential rows untouched. Original inputs are snapshotted to data/diagnostics/pre-residential/ before any rewrite. Since the Fang retirement the classification no longer takes rental samples, so the script's `--fang-samples` input is gone with it.
- New management Tab fetches independently of map/property filters; default district滨江, existing萧山 records remain selectable. Old header rental-management CTA navigates to this Tab.

### Source address provenance
- New imports keep `address=item.address` and `geographic_address=coordinates.formatted_address`; coordinates never seed a TMSF source address.
- Prepared directories run idempotent `mark_legacy_addresses(store,data_dir)` using `meta.source_address_provenance_v1`. Only imported TMSF sources whose address exactly matches saved geocoder output and have no recorded detail check are marked `address_origin=legacy_geocoder,address_verification_pending=true`. Preserve current address until a successful detail response; no startup upstream calls.
- TMSF details publish `address_origin=source_detail,address_checked_at,address_verification_pending=false` even for blank/暂无/未知. Type caches require address_checked_at and no verification pending. Marked identities absent from the name list are still retried. Failure/cancellation retains prior address and pending status, reports errors and retries next collection.
- Verified detail ingestion atomically replaces only a matched master's marked legacy address that still equals geographic_address; manual edits set address_origin=manual and are preserved. Save address_corrected audit with previous address. IDs, decisions, associations and histories remain unchanged. Current address gate reevaluates after correction.
- Good: legacy 襄七房 geocoder address → verified 暂无 → 不收录. Base: timeout → keep current record and retry. Bad: clear all addresses at startup or overwrite a manual address.
- Tests: `test_address_provenance.py` asserts new import separation, once-only marking, failure retention, actual missing-address correction, manual protection and cache bypass. Malformed/upstream detail failures use existing partial_failed reports, never successful empty-address updates.

## 4. API / Validation & Error Matrix
External /api/map/directory, backend /api/directory. Envelope success/data.
- GET communities?q&district&deleted&residential_state&page&page_size → items,total,page; GET/PUT/DELETE communities/{cid}; POST .../restore and .../merge {community_id}. Manual community creation is no longer exposed; new entries only arrive via /directory/collection → CommunityRegistry.create_from_source.
- GET sources?q&district&source&status&residential_state&page&page_size; GET sources/{rid} → candidates,possible_deleted,sample_count,residential_state and property facts (raw samples omitted); POST .../associate {community_id}; DELETE .../associate?community_id (reject target or unlink current); DELETE sources/{rid}; POST .../restore.
- POST auto-associate → matched; GET/POST/DELETE collection. POST accepts only sources=[tmsf], defaults to that single source and starts202. Amap or mixed-source requests return422; direct collect_names/DirectoryJob.start also reject amap before any work or report mutation.
- Invalid parameters422; unknown detail404; invalid/deleted target, duplicate rental-source binding, active collection or invalid restore409; SQLite/filesystem failures503. Upstream errors are per-source reports. Corrupt directory must not silently fall back to JSON.
- The generic source write paths (`associate`, `create_from_source`, `ingest`) refuse a new Fang association after the retirement: the request is rejected with the existing 409 mapping and the registry is unchanged. Historical Fang records stay readable, and explicit unlink/ignore keeps working.

## 5. Good / Base / Bad
Good: collect names → sufficient-evidence auto associations → manually resolve pending → delete whole community → restart/collect skips linked identities → explicit restore. Base: a source fails or returns repeated pages or ends before its reported count → retain discovered data and explain partial coverage. Bad: equate same name with same community; overwrite manual edits on startup; delete historical source samples; treat source limits as full-region collection.

## 7. Wrong vs Correct
Wrong: startup rewrites directory from binjiang_communities.json, restoring deleted communities. Correct: prepare once, then read the durable registry and record all user decisions there.
Wrong: after unlink, auction exact-name fallback immediately reattaches. Correct: when registry exists, only effective registry associations determine identity.
Wrong: source record is inserted then orphan community is created on a failed link. Correct: create_from_source validates pending status and creates+associates in one transaction.
