# 设计：从候选楼盘到正式住宅收录

## 已确认决定

- 用户要求先规划，再直接开发（2026-10-25）。
- 所有已有收录项目重新过新规则，不保留旧收录免审资格；人工决定、坐标、历史租金与法拍关联不删除。
- 实施与生产数据迁移分开。先提供只读迁移预览及影响清单，实际启用另行针对具体结果确认。

## 数据与职责

1. 透明售房网继续独立获取新房/二手房来源身份、名称、地址、用途、销售或挂牌证据。来源采集不调用高德。
2. `directory_workflow.materialize` 创建可核对的候选身份，不再要求先住宅收录。重用原主小区 ID；来源 ID、分期、拒绝关联、忽略和人工锁保持有效。
3. 高德位置选中的地点同时保存 POI ID、名称、类型码/文字、地址、坐标与来源时间。用途判断只读取这个选定地点，不再对全名搜索结果中多个商户的类型投票。
4. `directory_policy.eligibility` 统一计算正式收录，地图/租金/法拍目标仍只消费该统一结果。

## 状态

保留既有 `admission_state=admitted|excluded` 的兼容传输口径（excluded 是尚未收录集合），添加 `workflow_state=pending|admitted|excluded` 区分待处理和确定不收录，并添加具体 qualification。待补资料/待定位/待确认地点/待确认用途都属于 pending；不能因请求失败判为非住宅。

## 地点识别

- 滨江/萧山沿用既有支持范围；区外与区域冲突先纠正资料。
- 候选主体可包含住宅、商住、写字楼及园区主体；不能先按住宅白名单排除非住宅主体。
- 排除出入口、停车场、售楼处、楼栋和普通商户。主名或明确别名精确匹配优先；包含/去通名匹配只用于人工候选，不能自动确定身份，不合并不同分期或括号内物业类别。
- 唯一可靠精确主体可自动确定；多个主体或名称/区域证据冲突人工选择。手动坐标与人工选定 POI 区分：手动坐标不凭空产生高德类型，需另有人工用途证据。
- 分页以真实返回为准；保留已复现的 count 偏大/末页归零修正，重复页、失败、上限不冒充完整。请求预算应按真实 HTTP 请求计数，取消在每次请求前后生效。

## 收录矩阵

| 透明售房网 | 已确认主体类型 | 用途结果 |
|---|---|---|
| 住宅 | 住宅 | 自动通过用途门槛 |
| 明确非住宅 | 无须查询 | 确定不收录，可人工纠正 |
| 住宅 | 非住宅/商住 | 待人工用途确认 |
| 缺失/公寓/其他不明 | 任意 | 待补资料或人工用途确认 |
| 住宅 | 未确认/失败/缺类型 | 待定位/待确认/待补资料 |

人工住宅决定只覆盖用途门槛，区域、可靠位置和实际地址仍须有效；人工排除最高优先级。用途通过后，继续执行二手房 >=3 套挂牌门槛和已核验新房豁免。高德不能独自把透明售房网用途缺失变成住宅。

## 启用与历史重审

新流程使用单独版本标记，未启用保持旧口径。只读 preview 使用备份到内存的注册库，计算所有历史项目的新旧状态及来源物化变化。报告地图退出、租金采集目标退出、法拍待重新关联和人工保护项，保存快照指纹。apply 必须维护模式、备份、快照一致且无运行任务；启用后所有项目使用同一新规则，不允许 grandfather 自动保留。回滚只恢复版本/物化相关事务，已有新写入时拒绝整库覆盖。

## API 与界面

沿用目录、定位和确认入口；候选身份也能读取/查询/确认位置。详情同时展示透明售房网用途、选定高德主体类型、当前分类理由。用途复核批量入口转为选定 POI 的证据更新/重算，不能重新按名字混入其他地点。旧孤立 use_review 证据在新规则中不作为已确认主体证据。增加待处理/明确不收录的筛选，兼容原未收录列表。

## 范围边界与并行工作

不改新房浏览器采集器、价格/租金计算和法拍抓取；10-19 新房采集任务中的并行修改保持原样。当前未提交的真实分页修正作为输入，不重写。未来更新应按选定 POI ID 刷新其类型，不能自动改选其他主体。
