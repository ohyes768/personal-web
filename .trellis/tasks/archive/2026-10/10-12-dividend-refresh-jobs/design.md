# 技术设计

## 最终实现补充
用户已要求执行，2026-10-12 本地实现及验收完成。使用专属双线程 executor 和 RLock；同步受理路由仅准备任务，异步事件循环不执行采集。关闭先停止受理，再关闭 scheduler 并最多等待采集30秒，未强制取消工作线程。重启和写盘失败保守提供全部原始代码重试。每种保留20条近期记录。财务写入严格读取旧缓存；非强制指定范围也替换同代码旧行避免重复。旧200响应保留作同步部署的兼容期，确认调用方均升级后可删。部署现状不涉及n8n，遵循已完成的scheduler-lifecycle契约。

## 架构
在现有单 worker FastAPI 后端增加 RefreshJobManager，由 lifespan 创建和管理。用线程执行同步采集（asyncio.to_thread / 受控 executor），事件循环只处理任务受理、状态查询和页面请求。首版不增加外部任务队列。

任务按 kind=m120/financial 隔离，每种最多一个活动任务；不同种类允许并行，但各自串行采集保持现有请求间隔。后台管理器统一拥有资源锁，手动和定时都经过同一入口。进度回调通过线程安全机制发布；禁止跨线程直接修改 async 锁或未保护的记录。

## API 契约
- 保留 POST `/api/dividend/m120/refresh` 和 `/financial/refresh` 路径、请求参数，改为返回 HTTP 202：`{job_id, kind, status, total, reused, message}`。没有股票可更新时返回已完成的空任务，而非伪装采集成功。
- 启动前校验原有 force/节流/代码范围。校验失败沿用明确的 4xx；同类任务已在运行时返回已有任务的 202，`reused=true`，不启动第二个。
- 新增 GET `/api/dividend/refresh/jobs/{job_id}` 返回完整状态；GET `/refresh/jobs?kind=m120|financial` 返回该种最新任务，供页面重开恢复。
- 状态：queued、running、succeeded、partial_failed、failed、interrupted。记录包含 total、processed、succeeded、failed、remaining、started_at、finished_at、updated_at、简短错误说明及有限的失败代码列表。
- processed=succeeded+failed；remaining=total-processed。提前限流停止时，未处理股票保留 remaining，不计成成功；终态必须提供停止原因。
- HTTP 202 是受理状态，所有调用方必须迁移后才能发布。实施前检索其他调用方；外部旧脚本需要记录兼容说明。

## 数据写入
延续财务每10只分批保存和 M120 结束合并。写文件统一先写同目录临时文件，再 os.replace 原子发布。task progress 的成功采集数和最终保存失败应分别表达：保存失败则整体失败且不给页面完成成功提示。读数据仍用现有 reader 与跨周回退契约。

进度回调应每只股票更新一次，包括失败分支。M120 连续失败熔断必须返回可观测的未处理数量；财务 fetch_batch 保持既有返回数据类型，新增可选进度回调以兼容其他调用方。

## 任务持久化与重启
data/refresh_jobs/ 保存有限的近期任务记录，原子写入；不复制全部财务数据。进度可限频落盘，终态强制落盘。启动时将 queued/running 标记 interrupted，不自动续跑。页面显示“刷新已中断，可重试”，旧数据保留。保留每种至少最近一次任务；按有限数量清理历史记录，避免无限增长。

重试保持现有请求参数：force=true 仍重采指定范围；非强制任务遇到部分保存导致的90天节流时，需返回明确提示，引导强制重试失败/未处理代码，不能让任务永久不可重试。为中断任务保留原参数与剩余/失败代码，首版仍由用户主动触发。

## 前端
api.ts 声明任务 DTO；hooks.ts 启动刷新后轮询（建议2秒，隐藏页面降低频率），终态停止。组件卸载只取消轮询，不取消后台任务；恢复时从服务器查最新任务，不能只依赖 localStorage。断网显示“暂时无法查询进度”，保持 job_id 并可恢复，不能认定后台失败。

数据更新入口显示“已处理 X/Y，成功 A，失败 B”，运行时禁用同类重复操作。完成后检查原 status、更新相关表格；部分失败给出明确重试入口。保持现有抽屉布局，不重新设计整页。

## 定时任务与关闭协作
weekly_m120 启动同一后台任务；202 后异步等待其终态，最后记录实际结果。重复受理 reused=true 时记录 skipped/already_running。保留兼容旧200响应的迁移分支并明确删除时机。不得只把HTTP202计为成功。定时等待超时仅代表等待失败，不擅自取消线程中的采集。

与 `10-12-scheduler-shutdown-migration` 协调 lifespan 关闭：停止受理新任务、有限等待、保留未完成记录供下次启动标记中断。线程任务不能通过取消 asyncio wrapper 被误认为已停止，也不能在仍写文件时释放同类资源锁。

## 部署与回滚
前后端契约同步部署；部署前核对 nginx 错误日志中的 upstream timed out 及实际加载的超时配置。使用超过60秒的模拟任务验证，避免反复调用真实行情服务消耗额度。

部署后验证短请求仍可响应、页面刷新恢复、定时历史真实完成时间、重启中断状态。回滚前等待活动采集停止，防止新旧进程同时写数据；保留 CSV 与任务记录。延长代理超时只能作临时应急，不作为本任务验收方案。
