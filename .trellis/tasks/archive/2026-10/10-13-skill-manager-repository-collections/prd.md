# GitHub Skill 按仓库合集管理

## 目标
来自同一 GitHub 仓库的 skills 在管理台合成一个合集，例如 ai-berkshire。用户默认操作合集，需要时展开查看成员。

## 已确认事实
- SkillCard 已有 repository、path、deployments 等字段，可从现有登记派生合集，不迁移数据库。
- 同仓库已共用 Git 缓存；登记支持 batch，发布支持多 skill 队列。
- 当前安装使用每 skill 的 staging 快照与软链，本任务保持该机制。
- 前端契约要求下架入口位于部署看板，视图切换保留队列状态。
- 用户已认可按仓库归组、添加默认全选、合集操作与成员详情。

## 要求
R1 GitHub 管理看板按规范化完整 owner/repo 归组；不同 owner 的同名仓库不能合并。已有登记自动呈现，无需重新添加。自研列表保持原样。
R2 合集卡片显示仓库名、完整 owner/repo、已登记成员总数、各 Agent 已发布数、异常数与更新提示；已发布数不包含链接缺失项。明确成员数是已登记数量，不是远端仓库全部候选数量。
R3 默认折叠成员，展开显示原有单项状态与操作。搜索仓库名命中展示全体；搜索成员名/ID/简介或标签时展示匹配成员，同时显示匹配数/合集总数。
R4 合集“全部发布”按目标把完整已登记成员加入现有队列，去重且保留既有其他队列项，不直接写入 Agent。筛选后的合集也操作全部成员，按钮标明数量。
R5 GitHub 添加扫描成功后默认全选可登记候选，候选详情折叠；支持展开调整、清空及重选；新扫描清除旧选择。共享资源沿用已有安全预选规则。扫描与添加不隐含发布。
R6 合集提供检查更新与缓存恢复（同仓库一次后台任务），沿用已有 revision/发布契约；“检查更新”只检查，不声称已拉取或部署。新增远端成员需重新扫描登记，不自动安装；已登记路径消失需显示异常。
R7 部署看板按仓库归组，支持合集批量下架；只处理所选 Agent 的有效部署，逐项记录成功/失败，重试只针对失败项。管理看板不新增下架入口。
R8 保留成员单项登记删除、标签、导出等能力。MVP 不新增合集删除、统一 ZIP、合集标签或人工跨仓库合并。
R9 批量动作展示阻止/跳过/成功/失败明细；密码沿用现有写操作机制，禁止以合集状态覆盖成员真实结果。

## 验收
- 同仓库不同 path 只出现一张卡片；URL 的 .git、末尾斜线及大小写差异正确归并，不混合不同 owner。
- 部分已发布、链接缺失、缓存缺失等状态聚合正确，展开能定位具体成员。
- 重复点击合集入队不产生重复项；过滤不导致“全部”只操作可见成员。
- 添加无需手动挑选即可登记全体，仍能展开排除个别成员。
- 发布/下架部分失败时明确显示失败成员，重试不重复处理成功项。
- 既有单项登记、队列、发布、导出、自研管理与导航不回退。
- Windows 上完成针对性测试、类型检查和 lint；不安排 WSL/NAS 测试或生产部署。

## 不在范围
整包根软链、直接指向 Git 仓库、pack 表/API、NAS 清理、缓存/快照生命周期改造、自动纳入新增成员。

## 待实现时核实
检查更新和 Clone 接口的仓库级复用，以及当前发布结果结构；只有确实缺少能力时做最小后端扩展，不先建合集持久表。
