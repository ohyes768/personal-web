# 技术设计

## 边界
最小差距在 `XingfuliDiscovery.homepage()` 把身份与入口绑在一个HTML读取中，以及 `ProbeService` 假设候选资料已含种子。涉及 discovery、probe、discovery_checkpoint、必要的xingfuli_sources候选投影及其测试；不改已收录判定、注册表结构或租金统计。

## 数据流
搜索API -> 候选资料API -> 现有evaluate -> 唯一完整强证据自动解析 / 多候选待选 -> 新鲜身份与租房入口API -> 详情和同小区列表双归属核验 -> 原绑定事务。

## 接口与归一化
建议 `community_info(nid)` 只返回真实身份事实；`rental_entry(nid)` 返回种子、总数与入口状态。身份结构继续包含neighborhood_id/name/address/longitude/latitude/coordinate_system，并显式保留城市/区域检查。租房条目只作为种子线索，不作为归属授权。对 `homepage()` 现有调用逐一迁移，避免留下隐式两请求调用或把未知种子视为空入口。

## 断点和预算
搜索、资料、入口分别定义成功步骤和诊断名称；升级缓存版本或显式区分旧homepage键。每个HTTP步骤开始前查预算与取消，成功后立即持久化；新鲜身份和入口读取必须跳过旧授权。仅由同一次未过期决策持有新鲜标记，不能从缓存seed推断已核验。完整性、候选上限及搜索截断继续禁止自动绑定。

## 错误和兼容
HTTP成功还需status=0、结构正确、目标ID/城市一致。入口API失败不得回写有效空入口。保留业务stage、candidate_id/revision和人工选择流程；新增内部状态必须映射到已有可解释业务状态。默认不做HTML自动降级，避免静默增加请求和掩盖API异常。

## 性能与风险
冷启动唯一候选原常见1搜索+1主页+2核验=4请求，新流程可能1搜索+1资料+1入口+2核验=5请求。多候选情况下API拆分降低页面体积，但请求数量不天然减少；依赖持久化复用及按需入口，按相同目标、冷热缓存和限速条件测量。没有实测不得宣称加速倍数。

## 并行改动
列表抽样任务修改共享传输层，执行前确认其最新状态；此任务不改请求间隔或租金统计。保留旧HTML解析工具用于测试比较，不让它进入默认匹配路径。
