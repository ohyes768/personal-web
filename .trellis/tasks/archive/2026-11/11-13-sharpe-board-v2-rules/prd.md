# 夏普榜单 v2 入选规则与稳定性统计

## Goal

把夏普榜单入选规则从 v1 升级到 v2：在原有「成立≥3年 / 规模≥5亿 / 回撤≤30% /
经理≥5年 / 夏普≥0.8」之上，新增三道专业门槛
（IR ≥0.5、样本天数 ≥700、近3年同类排名前 20%），并在榜单上新增**稳定性统计**
展示列（近 12 周夏普达标周数等），让「谁一直好」这个判断从"单周达标"升级为
"持续达标 + 跑赢基准效率 + 同类相对领先"。

同时修复一个既有契约漂移：capture 冻结字段缺 `mgr_experience_years_max`，
导致榜单入选实际用 shortest-tenure 口径，与实时筛选不一致。

## 背景与动机

榜单当前只卡「夏普 ≥0.8」一道绝对门槛。实测最新周（2026-11-02）：
stock 29 只、discovery-stock 68 只。问题在于：
- 夏普高可能只是波动低 + 收益平庸，**没有衡量是否跑赢基准** → 需要 IR
- 绝对阈值 0.8 在牛熊年份松紧不同 → 需要同类分位做自适应参考
- 单周达标可能是运气，不是稳定 → 需要看近 12 周达标情况

## Requirements

### R1. v2 入选规则（三道新门槛）

在 v1 全部条件（成立≥3年、规模≥5亿、回撤绝对值≤30%、经理≥5年、夏普≥0.8）之上叠加：

| 门槛 | 字段 | 阈值 | 语义 |
|---|---|---|---|
| IR | `fund_risk_metrics.ir` | `>= 0.5` | 信息比率（相对基准的超额效率）；NULL 不命中 |
| 样本天数 | `fund_risk_metrics.sample_days` | `>= 700` | 3年窗口约750交易日，留50天缺口余量 |
| 同类排名 | `fund_achievement_rank` 近3年 `peer_rank` | 前 `<= 20%` | 自适应相对标准，替代纯绝对阈值 |

- **用户明确要求三道门都要**，上线后看效果再调参数。参数必须集中在 profile 常量，改参数=改版本。
- 同类分位阈值用「排名/总数 ≤ 0.20」计算；`peer_rank` 格式异常（无 `/`、分母 0、
  排名>总数）→ 视为无数据 → 不命中。
- 同类排名**陈旧容忍 90 天**：`as_of_date` 距今超过 90 天 → 视为无数据 → 不命中。
  （实测 509 只采集 universe 中 42 只超 30 天、0 只超 90 天。）

### R2. profile 版本隔离

- 新增 `(stock, v2)` / `(discovery-stock, v2)` 两套 profile，v1 保留在字典里不删。
- v2 与 v1 **完全隔离**：`sharpe_board_weeks.profile_version` 区分，聚合/发布/统计
  各查各的版本，绝不跨版本混合。
- 周任务默认发布 v2；v1 不再自动发布（无新周，历史快照冻结）。
- API `profile_version` 参数保持可用，默认改为 `v2`；未知版本仍 404。

### R3. v1 历史数据处理

- **先导出存档再删除**：把 96 周 complete 批次 + 9264 条观测导出为可恢复的存档文件
  （JSON + SQL 两种形态落 `data/archive/`，不入 git），档案内记录导出行数与哈希校验。
- 存档验证通过后，删除 `sharpe_board_weeks` / `sharpe_board_observations` 中
  `profile_version='v1'` 的全部行（含 failed/skipped 批次）。
- **不做历史回溯补算**（见 R4 限制说明）。

### R4. 历史回溯的限制（已实测，必须写进实现注释）

用户原意是「v2 上线后再补充历史数据」。实测结论：**只能部分补，不能全补**。

| v2 门槛 | 回溯可行性 | 证据 |
|---|---|---|
| 夏普 / 样本天数 | ✅ 可回算 | 净值 akshare 实时拉全历史 |
| IR | ⚠️ 大部分可，少数不可 | `fund_benchmark` 561 只 code，492 只覆盖≥700天；但有 62 只基准从 2026-11 才开始（其中 26 只曾上榜）→ 这些无法回溯 IR |
| 同类排名前 20% | ❌ **完全不可** | `fund_achievement_rank` 只有 6 个 `as_of_date`（2026-09-08~11-07），是快照非时序 |

**决策**：本任务不做历史回溯。理由：三道门里有一道（同类分位）在历史上根本不存在，
若强行用今日快照回填历史周，等于给历史标注了它当时不具备的信息（前视偏差），
统计结果不可信。v2 从上线周开始干净积累。

### R5. 稳定性统计展示（52 周窗口）

榜单**统计与图表统一卡在最近 52 周**（≈1 年），用户明确要求「刚好一年」。

- **窗口定义**：`WINDOW_WEEKS = 52`，从当前自然周周一向前数 52 个周一（含当前周）。
  等价于 364 天——**364 = 52×7 恰好是 7 的倍数，起点天然落在周一网格上**，
  不需要像现有 `range=1y`（365 天）那样做对齐修正。
- **`listed_weeks` 口径改为窗口内计数**：近 52 周内在榜几周（0~52），不再是全历史累计。
- **`consecutive_weeks` 同样只在窗口内数**（连续段若跨过窗口起点则截断到窗口边界）。
- **图表周历恒为 52 个周一**（历史不足 52 周时按实际周数，从首周开始）。
- **`near_12w_qualified`**：最近 12 个 complete 周中夏普 ≥0.8 的周数（0~12）；
  不足 12 周按实际周数计，返回分母避免误导（如 `10/12`、`4/6`）；无历史返回 null。
- **同类排名分位展示**：当前同类排名百分位（如「同类前 14.2%」），带 `as_of_date`。

**窗口截断的连带后果（必须知晓）**：
`min_weeks` 默认 1，而窗口截断后**一年没上过榜的基金 `listed_weeks` 变为 0 → 被默认筛掉**。
因此本改动在默认视图下实际效果接近「榜单只保留近一年还行的基金」。
这是符合预期的（榜单本就该反映近期状态），但必须在页面上把口径写清楚
（如标题或副标题注明「近 52 周」），避免用户误以为在看全历史资历。

**残余的历史价值**：v2 之前的历史不再影响在榜周数，但原始观测行仍保留在库里
（供走势页查「这只基金曾经是否在榜」）。窗口只作用于榜单页的统计与图表，
**不删除任何观测数据**。

理由：实测连续性门槛（近12周≥10周达标）只筛掉 1~3 只，净化作用有限，故不入入选规则；
但它对「排雷」有价值——一只在榜很久的基金若近12周达标数在下降，是衰退信号。

### R6. 修复 capture 字段缺失（既有缺陷）

- `sharpe_capture.BASE_ROW_FIELDS` 增加 `mgr_experience_years_max`。
- 实测证据：最新周 97 只成员 `evidence_json.base` 中带该字段的是 **0/97**。
- 后果：`entry_predicate` 的 `min_mgr_exp` 优先读 `_max`（共管取最长，避免误杀
  "老将+新人"），字段缺失时静默回退到 `mgr_experience_years`（取最短）→
  榜单入选口径比实时筛选更严、且会误杀，属契约 §2 注释描述的语义漂移。
- 修复后必须有等价性测试锁定：冻结数据谓词结果 == 实时 SQL 筛选结果。

### R7. 前端

- 榜单页默认 `source=discovery-stock`、`profile_version=v2`。
- 新增「近12周达标」展示列 + 同类分位列；列宽与现有表格风格一致。
- profile 切换时，页面需明确提示当前规则版本（避免用户以为在看 v1 数据）。
- 三处同步：`src/api/models.py` ↔ `apps/fund-select/src/lib/sharpe-board.ts` ↔ 页面消费。

## Constraints

- **不改 v1 历史行的任何字段**（导出存档是纯读取；删除是整行删除，不改写）。
- 三道新门槛必须走 `entry_predicate` 同一份谓词实现，实时筛选与 capture 冻结数据
  共用，**禁止单改一边**（契约 §2，由等价性测试锁定）。
- `min_sharpe`（记录参数）与 `min_latest_sharpe`（展示参数）必须继续分开。
- 同类排名查询不得 JOIN 进发布主事务导致发布变慢：用一次批量查询预取（≤500 codes）。
- 时间列沿用 UTC 挂钟 naive 存储，展示层转北京时间。
- 不改动 bond 两条链路（不含夏普 capture）。

## Acceptance Criteria

### 规则与发布
- [ ] AC1：v2 profile 存在且 `algorithm_version` 递增；`get_profile('stock','v2')` 返回
      含三道新门槛的 filters；`get_profile('stock','v1')` 仍返回旧规则（未被污染）。
- [ ] AC2：`entry_predicate(ir_min=0.5, sample_days_min=700, peer_pct_max=20)` 与实时 SQL
      筛选结果**完全等价**（构造含 NULL / 边界等号 / 格式异常 peer_rank 的用例）；
      NULL 值一律不命中。
- [ ] AC3：周任务默认发布 v2；发布后 `sharpe_board_weeks.profile_version='v2'`，
      v1 无新周产生。
- [ ] AC4：三道门叠加后，用最新周数据测得的留存数与调研一致
      （stock 29→10、discovery-stock 68→33，允许因数据刷新小幅波动）。
- [ ] AC5：任一门槛数据缺失（ir NULL / sample_days NULL / 无同类排名 / 排名陈旧>90天）
      的基金不入选，且进 `diagnostics`（可区分"数据缺失"与"不达标"）。

### 历史处置
- [ ] AC6：导出脚本产出可恢复存档，含批次行数、观测行数、sha256 校验；用存档重建后
      行数与哈希一致。
- [ ] AC7：删除后 `SELECT COUNT(*) FROM sharpe_board_weeks WHERE profile_version='v1'` == 0，
      且 `v2` 行、其他表（funds / fund_risk_metrics / manager_tenures 等）零影响。

### 统计与展示
- [ ] AC8：`near_12w_qualified` 统计正确：完整 12 周时返回 `n/12`，不足时返回 `n/实际周数`；
      无 complete 周历史返回 null 而非 0。
- [ ] AC9：同类分位展示值 = `rank/total*100` 保留 1 位小数，同时返回 `as_of_date`。
- [ ] AC9b：52 周窗口正确：`listed_weeks` 只数窗口内周数（构造 100 周历史，验证返回 ≤52）；
      窗口起点落在周一且与当前周相差恰好 51 个整周（364 天）；
      历史不足 52 周时按实际周数返回，不补零；图表 `weeks` 长度 == 窗口周数。
- [ ] AC9c：窗口截断不删除数据：`sharpe_board_observations` 总行数在改动前后一致，
      仅聚合口径变化。
- [ ] AC10：前端两列渲染正确，profile 版本与「近 52 周」口径提示可见；1440/390 无横向溢出；
      翻页不重建图表（沿用 `dataSignature` 契约）。

### 缺陷修复
- [ ] AC11：capture 冻结的 `base_rows` 含 `mgr_experience_years_max`；
      新增测试断言该字段存在于 evidence_json。
- [ ] AC12：修复后用同一批数据跑冻结谓词与实时 SQL，入选集合完全一致（回归锁定）。

### 测试
- [ ] AC13：`pytest` 全绿；新增测试覆盖三道门槛的边界（等号通过、NULL 不通过、
      90 天陈旧边界、peer_rank 格式异常）。
- [ ] AC14：前端 `node --test` + `tsc --noEmit` 通过。

## Out of Scope

- 历史回溯补算（R4 已论证不可行）
- 规模上限门槛（实测只影响 2 只，且逻辑不成立，已废弃）
- 连续性门槛进入选规则（实测只筛 1~3 只，降级为 R5 展示统计）
- 债基链路（无夏普 capture）
- 走势页本体（另一会话在做的 `/sharpe-trend` 任务）
