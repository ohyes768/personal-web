## 2. 对照四条要求的缺口

### 要求 1：评估按钮，未评估/已评估都有，已评估的叫「再评估一次」

**现状：已评估的行没有行内评估入口。**

行内主按钮区只认四种情形（`FavoritesTrackingTab.tsx:583-596`）：评估中 / `pendingApply` / `derived.state === 'unevaluated'` / `derived.state === 'failed'`。

- 已应用（有报告、已生效）的行：`deriveFavoriteTrackingState` 在 `report.status === 'ready'` 时把 `state` 置为 `'pending_apply'`（`valuation.ts:279`），这个值**不会**落进 `unevaluated` 或 `failed` 分支 → 主按钮区为空。
- 次链接区的「评估挡位」条件是 `!report && derived.effective`（`:604`），有报告的行同样拿不到。
- 唯一入口在报告弹窗底部的「重新评估」。

### 要求 2：状态可见，进行中能看到

基本够用：徽章有「评估中」（脉冲）。建议补一行「队列第 N 位」，让行内不用跳到队列面板才知道排第几。

### 要求 3：评估完（失败或成功）都有会话下载

功能上有（后端台账保证失败那次重启后仍可下载）。**但位置与口径错位：**

```
sessionRunId = live?.run_id ?? report?.run_id        // 最新一次尝试
```

取的是**最新那次尝试**（失败就是失败那次），而「评估 / 版本」列永远显示 `report.evaluated_at`（**报告**的时间）。失败行的实际渲染是：

```
[评估失败]              ← 状态列
11-12 09:30 / v1.2      ← 上次【成功】报告的时间
[⬇ 下载会话记录]        ← 下载【今天崩掉】那次的会话
```

按钮挨着一个不属于它的时间。

### 要求 4：评估完成后查看报告，要有独立阅读页

现状只有弹窗。需新建 `/valuation-reader`，对齐 `/quality-reader`（`QualityReader.tsx` / `lib/quality-reader.ts` / `app/quality-reader/page.tsx`）。

## 3. 核心模型：三个独立事实

一行其实有**三件互不相干的事**，现状把它们揉成了一个 `derived.state`：

| 事实 | 含义 | 表达什么 |
|---|---|---|
| **attempt**（最近一次尝试） | 排队 / 运行 / 失败 / 成功 / 取消 | 状态徽章、时间、会话下载 |
| **report**（最新一份报告） | 有没有、能不能出价、待应用还是已生效 | 挡位列、应用按钮 |
| **effective**（当前生效挡位） | 现在监控用的四条线 | 挡位列、区间列 |

揉在一起的直接后果：

1. **失败盖住待应用**：`deriveValuationEvalState` 先判 `live === 'failed'` 就返回 `'failed'`（`valuation.ts:255`），而 `derived.pendingApply` 仍为 `true`。行内徽章显示「评估失败」，但主按钮区因 `pendingApply` 优先命中而给出「应用 / 查看报告」（`:585`）——用户在应用一份自己没意识到已经过期的报告，且**没有重试入口**。
2. **报告已应用时 `derived.state` 仍是 `'pending_apply'`**（`:279`），语义失真；连带 `candidateLevels` 在报告已生效时也算出来（`:389`），只是恰好没被渲染。
3. **时间/版本与挡位条对不上号**：挡位列画的是 `levels`（生效），版本列写的是 `report`（最新报告），待应用时两者不同源。

**设计原则**：状态列讲 attempt，挡位列讲 effective + report，操作列讲「你现在能做什么」。

## 4. 交互设计

### 4.1 表结构（7 列 → 6 列）

```
股票 / 基本面 │ 现价（元） │ 挡位（元） │ 区间 │ 评估 │ 操作
```

「评估 / 版本」与「评估状态」合并为一列「评估」，理由：版本与时间是状态的注解（同一件事的出��），拆两列既重复又让注解跑到主语前面。

### 4.2 「评估」列 = attempt 的状态 + 溯源 + 这份评估的产物入口

```
[待应用]
11-14 09:30 · v1.2
查看报告  下载会话记录
```

三行分别是：**这次 attempt 的状态**、**它的出处（时间 + 版本）**、**它的两个产物入口**（报告正文、会话记录）。

「查看报告 / 查看缺口」放在这一列而不是操作列（2026-11-15 定稿）：它和「下载会话记录」是一对——**都是这次评估的产物**，不是对这只股票的动作。放在一起既合语义，又把操作列腾给真正要按的按钮。

| 情形 | 徽章 | 第二行 |
|---|---|---|
| 从未评估 | 待评估 | — |
| 排队/运行 | 评估中（脉冲） | 队列第 N 位 |
| 失败 | 评估失败 | `11-15 10:02 · 失败` + 下载（本次失败会话） |
| 取消 | 已取消 | `11-15 10:02` + 下载（被取消那次会话） |
| 成功 | 评估完成 / 待应用 | `11-14 09:30 · v1.2` + 下载（本次成功会话） |
| 纯手工挡位（没走过 Hermes） | **手工挡位** | 挡位配置时间 |
| 报告版本 ≠ 已部署版本 | 同上 | 版本号后挂 `需重评` 角标 |

要点：徽章、时间、版本、会话下载**四者永远指向同一次 attempt**。这同时修掉 §2 要求 3 的错位。

「手工挡位」是新增文案：现状手工挡位行的徽章是「待评估」，与旁边的「手工配置」看着矛盾。

### 4.3 「挡位」列 = 只画一条生效条，候选不进表格

**一条条就够。** 两张条叠着画放不下（行高翻倍），而且候选那套价已经有专门的地方放。

```
[生效价格条]
生效于 11-14 09:30 · 新挡位待应用     ← 只在「有待应用候选」时出现这一行
```

| 情形 | 画什么 | 脚注 |
|---|---|---|
| 有生效挡位，无候选 | 生效条 | `生效于 {应用时间}` —— 评估状态列已说明这次评估的时间与版本，这里不重复 |
| 有生效挡位 + 有候选 | 生效条 | 同上（"旧挡位仍生效"由评估状态列说，不在这里重复） |
| 无生效挡位，有候选 | 候选条（弱化） | `待应用 · {评估时间} · v{版本}` |
| 都没有 | — | 现有文案（尚未评估 / 评估失败，暂无挡位 / 资料不足：摘要） |

这一行脚注的作用只有一个：**消解「条和时间对不上号」**。有了它，读者看到的是「条 = 11-14 应用的那套」「评估列 = 11-15 新算的那套」，两个时间各归各位，不再互相冒充。

**脚注不写生效挡位的版本号。** 报告按 code 覆盖写（`valuation_service.py:398` `merged[report.code] = record`），候选报告成功后旧报告就被顶掉了——生效挡位那套当年是用哪版 skill 算的，**事后已经查不到**。写上去是假信息。版本号只属于「报告」，归评估列管。生效挡位可靠可查的只有应用时刻（`alerts.updated_at`，`routes.py:3624`）。

**候选那套价在哪看**（都不占表格宽度）：

| 位置 | 内容 |
|---|---|
| 「应用」→ 确认卡 | 已有新旧四档对比表 + 应用后落在哪一区；**补一行新报告的评估时间与 skill 版本** |
| 「查看报告」→ 阅读页 | 四档价格卡（与生效挡位划线对比）+ 元数据行（时间/版本本来就有） |

表格里候选的存在感由三处承担，都很醒目：黄色「待应用」徽章 + 「应用」按钮 + 顶部「N 份挡位评估等待确认」提示条。

### 4.4 「操作」列 = 只放对这只股票的动作

单行按钮组，全部落在同一行：

| attempt | report | effective | 按钮 |
|---|---|---|---|
| 无 | 无 | 无 | `[评估挡位]` |
| 排队/运行 | 任意 | 任意 | `[评估中…]` 禁用（取消在队列面板） |
| 失败 | 无 | 无/有 | `[重试评估]` |
| 失败 | 有待应用 | 有 | `[重试评估] [应用]` ← 修掉「失败盖住待应用」 |
| 成功 | 待应用 | 无/有 | `[应用] [再评估]` |
| 成功 | 已应用 | 有 | `[再评估]` |
| 成功 | 非 ready | 无/有 | `[再评估]` |

末尾固定一个 `[挡位设置]`（次要动作，手工编辑四条价格线）。

**这一列不放任何链接**——报告入口已经归到「评估」列，操作列只留按钮。

「再评估」在存在待应用报告时先弹一次确认：**重新评估会覆盖当前待应用的报告（尚未生效），已生效挡位不受影响。**

## 5. 三条主线动线

1. **首次评估**：收藏跟踪 → `[评估挡位]` → 徽章「评估中」→ 完成 → 「待应用」→ `[应用]` → 确认卡 → 生效 → 徽章「评估完成」
2. **再评估**：已应用行 → `[再评估]`（有待应用报告时先确认覆盖）→ 跑完 → 新报告「待应用」→ `[应用]`
3. **失败排查**：徽章「评估失败」+ 原因 → 评估列第二行下载**本次**会话 → 读 markdown 定位 → `[重试评估]`

**部署** — nginx `location /dividend/` 已能代理 `/valuation-reader`，**不需要改 conf**。

## 6.1 实现备注（落地时与设计的差异）

1. **时间格式自己拼**：`formatMoment` 用 `MM-DD HH:mm` 手工拼，不走 `toLocaleString`——各浏览器 locale 的分隔符不一致（Chrome zh-CN 出的是 `11/11 10:00`），自己拼才稳定。
2. **链接的可访问名**：行内「查看报告」带 `aria-label="查看报告 · 公司名"`，可见文案必须包含在可访问名里（WCAG 2.5.3），因此把公司名放在文案后面而不是替换掉它。
3. **非 ready 报告的摘要不再重复**：原先「资料不足」区块与「摘要」章节各渲染一次 `report.summary`，阅读页上肉眼可见重复——区块只保留状态与缺口，摘要由摘要章节承载。
4. **「生效于」脚注不重复「待应用」**：挡位脚注只写生效时间，「旧挡位仍生效」由评估状态列说。
5. **报告入口从操作列移到评估列**（2026-11-15 定稿）：「查看报告 / 查看缺口」与「下载会话记录」是一对，都是这次评估的产物；操作列腾出来后只剩真正要按的按钮，整列单行排得下。
6. **失败原文不渲染在行里**（2026-11-15 定稿）：后端原文可能很长（如「run xxx 超过 3600s 未完成（最后状态 running）」），直接渲染会把行撑高三行。行里只留「评估失败」徽章，原文放进徽章的 `title` 悬停提示——与选股关注里评级失败行的做法一致。队列弹框里的原文改成单行摘要 + `title` 全文。

## 7. 风险与待定

### 已定（2026-11-15）

1. **重新评估覆盖待应用报告 → 弹确认**。文案：「重新评估会覆盖当前待应用的报告（尚未生效），已生效挡位不受影响。确认重新评估？」取消 = 不动。
2. **阅读页不收失败的股票**。集合 = 有估值报告的股票；失败的没有报告可读，失败信息与失败会话下载留在收藏跟踪表。
3. **报告弹窗删除**。估值报告只有阅读页一个入口，避免两套渲染走偏。行内「应用」仍走紧凑确认卡（快操作，不是阅读）。

### 仍待定 / 风险

4. **失败与待应用并存的产品口径**：失败的那次报告仍在「待应用」计数里（顶部提示条）。拆分后行内要明确标出「上次报告待应用」，避免用户以为没有待办。
5. **挡位设置弹框**留在表内，不进阅读页。
6. **移动端**：阅读页沿用 `quality-reader` 的移动端样式与固定底栏。
